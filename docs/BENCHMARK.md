# OpenCodeCanvas 基准测试：编排价值度量（对外版）

> 一句话：**同一个模型，开不开编排，差距有多大？** 这是可复现的实验，不是宣传语。

## 背景

市面上的 agent 基准（SWE-bench 等）度量的是「单个 agent 能否解出单个 issue」。OpenCodeCanvas 的主张不同：**项目级任务编排**——先把成功标准写清楚，再规划执行，最后由独立验收员逐条给证据。这套主张目前没有现成榜单能度量，所以我们自建了 `bench/orchestr`：

- 任务来自真实开源仓库（tabulate / tenacity / schedule / toml / tablib），要求实现仓库里**当前不存在**的功能
- **判据在运行之前定义并提交进版本库**（evaluation-first）
- 验收由**独立脚本**执行（不在 agent 工作区内），并检查 agent 不得改动既有测试
- 两条实验臂使用**同一个模型、同一把 key**：全编排管线 vs 一次直调基线
- **失败与超时如实计入**，全部原始结果 JSON 随仓库公开

## 首期数据（8 任务，n=8）

| 任务 | 单发直调 | 全编排管线 |
|---|---|---|
| schedule 加 jitter | ✅ 20s | ✅ 14.2min |
| tabulate 加 CLI 排序 | ❌ 实现错误 | ❌ 功能未达标（v3 重跑） |
| tabulate 加 Decimal 定点 | ❌ JSON 解析失败 | ❌ **篡改既有测试被拦截**（唯一一例） |
| tabulate 加 CLI 编码 | ❌ 4s 实现错误 | ❌ 功能未达标 |
| tabulate 加 CLI 转置 | ❌ 4s 实现错误 | ❌ 功能未达标 |
| tenacity 属性化重试 | ❌ 输出非 JSON | ❌ 功能未达标 |
| toml 加 sort_keys | ❌ JSON 截断 | ❌ 功能未达标 |
| tablib 加 sort_by | ❌ JSON 截断 | ❌ 功能未达标 |
| **合计** | **1/8** | **1/8** |

管线臂的 6 行 ❌ 为 2026-10-22/23 数据修正：早期批量运行存在项目切换竞态（详见 `results/summary.md` 数据修正史），受影响任务已在「每任务专属应用实例 + 根目录断言」纪律下重跑——结局仍为诚实失败，0 例篡改；v3 重跑还把一次早期通过改判为失败（见脚注）。

`*` 早期一次通过（tabulate 排序，925s）在 v3 纪律干净重跑下**未复现**——已从表中撤下，过程见数据修正史。

**最有价值的发现**：验收链的价值在失败侧成立——1 例「agent 靠修改仓库既有测试适配实现：改考卷而不是改答案」被完整性检查拦截（任何「agent 自称完成 + 现场测试通过」式评估都会漏掉它）；另有 6 例「管线收工/停止、但判据没全过」被独立验收脚本逐条如实判 FAIL。基准本身同样被审计：一次成本审计抓出了 runner 的批量隔离缺陷（3 个结果作废重跑）；v3 干净重跑又把我方头条从「编排 2/8」修正为「编排 1/8」——tabulate-sort 的早期通过未被复现，照实登出。**评估系统在被评估，包括我们自己改自己的分**。

## 已验证的产品能力（与本基准同源）

- HumanEval（函数级）：基线 58/60 → 管线 93–97%
- 上下文治理与循环内压实；长时程硬化（恢复清扫、预算/步数上限）
- 独立验收员逐条 PASS/FAIL + 低置信度换模型交叉复核
- 本地 Jev 路由（$0 决策）与验收价值学习（跳过历史上从不出错的验收轮）

## 诚实边界

- 任务集与验收脚本由我们编写（判据先行、开源可审计，但仍是自建基准）
- Windows 单平台；单模型（deepseek-chat）首期；样本量小
- SWE-bench（行业通用分）待 Docker 环境就绪后补充
- **数据修正史（对外公开）**：①早期验收脚本有 bug，被我们抓出并修正（「4 例篡改」修正为 1 例）；②2026-10-22 成本审计发现批量跑存在项目切换竞态，受影响任务作废重跑（每任务专属应用实例）；③token 成本仅 v2 runner 起开始记账，更早的运行（schedule/tabulate-sort/tenacity 试点）没有账本。基准的自我纠错记录本身就是方法论的一部分。
